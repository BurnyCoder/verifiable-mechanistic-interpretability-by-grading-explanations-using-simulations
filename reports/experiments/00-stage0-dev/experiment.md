# Experiment 00 — Stage 0: tooling and smoke tests on the dev target

*Development stage. The dev target (`wd1_s10`, key frequencies {19, 31, 45, 47}) is never used for hypothesis tests;
results here only informed tooling. Preregistration §9.*

## Goal

Make every part of the pipeline work end to end on a target that is not reported: explainer, reference compiler,
grader, sandbox isolation, local LLM throughput, and the simulator agent (planned: Qwen in OpenCode; used from round 1:
Claude Haiku 5.5 in Claude Code).

**What this shows (dev only, descriptive):**
- **Output KL cannot tell a wrong-frequency explanation from a right one.** W-freq builds a working model with tiny
  output KL, but its hidden states share almost nothing with the target (HS ≈ 0.1) — exactly the failure mode H3
  predicts. E0/E1 (frequencies unknown, compiler uses its default set) behave the same way.
- **True detail raises HS:** E2 → E3 → E4 increase monotonically.
- **The Pizza control (W-alg) is hard to separate** from the Clock explanations on HS: both use the same frequencies,
  and linear regression across the residual stream sees mostly the shared frequency subspaces.
- **On the dev target the compiler's W-scramble build is not separated by the primary HS** (per-neuron frequencies
  redrawn within the key set leave every frequency subspace intact) but is by the secondary matched-neuron correlation
  (E4 vs W-scramble). This does not hold everywhere: on T0 the literal scrambled build scores
  <!-- v:a5-scr-t0 -->0.09<!-- /v --> lower (audit 5).
- **W-role breaks behaviour** (accuracy ≈ 1 %): the MLP reads frequencies the embedding does not carry; its resid_mid
  still matches (the embedding and attention are correct) while mlp_post is dead.
